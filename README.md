# UPPE_THZ_DC на C++

Порт фортрановской программы `UPPE_THZ_DC` (`PARALLEL.f90` + `FME_r.f90`): распространение
оптического импульса и генерация ТГц-излучения в воздухе во внешнем постоянном поле
(UPPE для оптики и ТГц, схема RK2 с промежуточной точкой, ионизация по таблицам N2/O2,
керровская, плазменная и омическая нелинейности).

По умолчанию программа делает то же, что фортрановский код: те же сетки, константы,
порядок операций, расписание вывода и те же файлы в `res/`. Исключение — исправленная нормировка
энергии (см. «Ошибки фортрановского кода»): поле в 1.0761 раза больше фортрановского. Добавлены останов по `--z-max`,
ограничение по времени и продолжение расчёта с чекпоинта.

## Зависимости

- CMake ≥ 3.21, компилятор C++17 с OpenMP.
- Один из двух бэкендов:
  - **MKL** (Intel oneAPI, Windows или Linux): FFT через FFTW3-обёртки MKL, BLAS через MKL;
  - **FFTW3 + OpenBLAS** (GCC/Clang): libfftw3 (double) и OpenBLAS ≥ 0.3.10.

BLAS и FFT вызываются из параллельных OpenMP-циклов, поэтому библиотеки работают
в однопоточном режиме (MKL линкуется как `sequential`, для OpenBLAS вызывается
`openblas_set_num_threads(1)`). Число потоков задаётся только OpenMP.

## Сборка

### Windows, Intel oneAPI (icx + MKL) — рекомендуется

```bat
call "C:\Program Files (x86)\Intel\oneAPI\setvars.bat" intel64
cmake --preset mkl-windows-icx
cmake --build --preset mkl-windows-icx
ctest --preset mkl-windows-icx
```

### Windows, Visual Studio 2022 + MKL

```bat
call "C:\Program Files (x86)\Intel\oneAPI\setvars.bat" intel64
cmake --preset mkl-windows-msvc
cmake --build --preset mkl-windows-msvc
ctest --preset mkl-windows-msvc
```

`setvars.bat` нужен и при запуске: он кладёт DLL MKL в `PATH`.

### Linux, MKL

```sh
source /opt/intel/oneapi/setvars.sh
cmake --preset mkl-linux
cmake --build --preset mkl-linux -j
ctest --preset mkl-linux
```

### Linux, GCC/Clang + FFTW3 + OpenBLAS

```sh
sudo apt install libfftw3-dev libopenblas-dev   # или аналог
cmake --preset fftw-openblas
cmake --build --preset fftw-openblas -j
ctest --preset fftw-openblas
```

Опции CMake:

| Опция | По умолчанию | Смысл |
|---|---|---|
| `UPPE_BACKEND` | `MKL` | `MKL` или `FFTW_OPENBLAS` |
| `UPPE_NATIVE` | `ON` | `-march=native` / `-xHost` / `/arch:AVX2` |
| `UPPE_BUILD_TESTS` | `ON` | собрать тесты |
| `UPPE_FOCUS_CM` | `20.0` | фокусное расстояние `focus`, см (константа компиляции; от него зависят `a0` и `Ldifr`) |
| `UPPE_ZSIC_CM` | `18.0` | `zsic`, см: начало расчёта, первый шаг `dz = zsic/Ldifr`; меньше `focus` |
| `UPPE_PRELENS_CM` | `400.0` | путь пучка от источника до линзы, см (`c::prelens`); `0` — исходный профиль стоит прямо на линзе |
| `UPPE_ENERGY_MJ` | `0.5` | энергия импульса, мДж (`c::WW0`) |
| `UPPE_A0_CM` | пусто | единица длины `a0`, см; пусто — `a00·(1 − zsic/focus)`, как в Фортране. Задав её явно, сетку отвязывают от `zsic` |
| `UPPE_RMAX` | `20.0` | радиус оптической сетки в единицах `a0` (`c::Rmax`); физический радиус `Rmax·a0` |
| `UPPE_NR_OPT` | `1000` | число узлов оптической сетки (`Sizes::nR_opt`); шаг по радиусу примерно `π·Rmax·a0/nR_opt` |

Шаг оптической сетки держится постоянным, если `UPPE_RMAX` и `UPPE_NR_OPT` меняются в одно и то же число раз.
Сетка `FirstStep` имеет радиус `Rmax·a0·nR_first/nR_opt` (3.2 см при значениях по умолчанию и, например, при
`A0_CM=0.01`, `RMAX=40`, `NR_OPT=2000`).

`-ffast-math`, `/fp:fast` и режим icx по умолчанию (`-fp-model=fast`) отключены намеренно:
порт воспроизводит фортрановский порядок операций, а fast-math его меняет.

## Запуск

```sh
uppe_thz_dc [--z-max <см>] [--threads <n>] [--data-dir <папка>] [--out-dir <папка>]
            [--checkpoint <файл>] [--resume <файл>] [--wall-limit-min <мин>] [--min-free-gb <ГБ>]
            [--max-steps <n>] [--snap-dz-cm <см>] [--linear]
```

- `--z-max` — остановиться, когда `z*Ldifr` достигнет заданного значения (в см).
  Без флага цикл бесконечен, как в Фортране; все файлы сбрасываются на диск каждый шаг,
  так что прерывание процесса вручную ничего не теряет.
- `--threads` — число потоков OpenMP (по умолчанию `OMP_NUM_THREADS` или все ядра).
- `--data-dir` — папка с `N2.dat` и `O2.dat` (по умолчанию текущая; копии лежат в `data/`).
- `--out-dir` — куда писать `res/`, `SpSIC.dat`, `Incident.dat` (по умолчанию текущая папка).
  Подпапки `res/IS`, `res/Fl`, `res/kw_THz`, `res/Or`, `res/Ne`, `res/IO` создаются сами.
- `--wall-limit-min` — остановиться в конце шага, если следующий шаг (с запасом 1.5 от самого
  долгого из пройденных) не укладывается в заданное время работы программы.
- `--min-free-gb` — остановиться в конце шага, если на диске `--out-dir` свободно меньше заданного
  (в ГБ по 10⁹ байт). Запас должен вмещать ещё один снимок (~1.35 ГБ) и чекпоинт.
- `--max-steps` — остановиться после `n` шагов по `z` (считая шаги предыдущих запусков).
- `--snap-dz-cm` — писать снимки через равные интервалы (в см) вместо фортрановского расписания
  (0.25 см, на участке 19–20.2 см — 0.1 см).
- `--linear` — выключить нелинейный отклик (Керр, ионизацию, токи): линейное распространение падающего поля.
  Эталон положения и высоты линейного фокуса; шаг дешевле, ТГц-поле остаётся нулевым.
- `--checkpoint` — при досрочной остановке (`--wall-limit-min`, `--min-free-gb`, `--max-steps`, SIGINT/SIGTERM)
  записать в файл состояние: поля `E(w,kr)`, `E_THz(w,kr)`, `z`, расписание снимков, `Imax`, номер шага
  (около 720 МБ при производственных сетках), а также `focus` и `zsic`, с которыми собрана программа;
  продолжить с другими `UPPE_FOCUS_CM`/`UPPE_ZSIC_CM` нельзя. Файл пишется через временный и переименовывается.
  Первый сигнал просит остановиться после текущего шага, второй убивает процесс.
- `--resume` — продолжить с чекпоинта: `FirstStep` и запись файлов сеток пропускаются,
  `res/Imax.dat`, `res/Nemax.dat`, `res/Energy.dat` дописываются, снимки продолжают расписание.
  Результат побитно совпадает с непрерывным расчётом (проверяется тестом `checkpoint`).

Код выхода: 0 — достигнут `--z-max`, 75 — досрочная остановка (чекпоинт записан, если задан), 1 — ошибка.
Номер каждого законченного снимка дописывается в `res/snapshots.txt`.

Пример:

```sh
export OMP_PROC_BIND=close OMP_PLACES=cores
./build/fftw-openblas/uppe_thz_dc --data-dir data --out-dir run1 --z-max 30
```

Память при производственных размерах (`nt_all=524288`, `nR=16000/1000/5000`):
около 2.2 ГБ на этапе FirstStep и около 3.5–4.5 ГБ в основном цикле (из них ~16 МБ на поток);
фортрановская версия требует ~8 и ~7 ГБ.

## Запуск в GitHub Actions

Workflow [`.github/workflows/simulate.yml`](.github/workflows/simulate.yml) собирает программу
на `ubuntu-latest` (бэкенд FFTW3 + OpenBLAS), прогоняет тесты и считает до `--z-max` цепочкой
сегментов. Задача GitHub живёт не больше 6 часов, поэтому каждый сегмент:

1. останавливает расчёт так, чтобы вся задача уложилась в `budget_minutes` (по умолчанию 330)
   от своего старта, с запасом 25 минут на упаковку и выгрузку, — или раньше, когда на диске
   остаётся меньше 6 ГБ (`--min-free-gb`; перед сборкой удаляется ненужный предустановленный софт);
2. сохраняет чекпоинт в artifact `ckpt-<tag>-segNN` (хранится 7 дней);
3. сам запускает следующий сегмент (`gh workflow run`, `segment+1`, `resume_run_id` = свой run id),
   который скачивает чекпоинт и продолжает с того же шага. Вся цепочка собирается из одного
   коммита (`code_sha` фиксируется в первом сегменте). Сегменты одного `tag` не идут одновременно.

Запуск: Actions → **Simulate** → **Run workflow**, указать `z_max` (см), `focus` и `zsic` (см)
и новое имя цепочки `tag`, остальные поля оставить по умолчанию. `z_max = none` — без ограничения
по `z`: цепочка идёт, пока её не отменят или пока не будет пройдено `max_segments` сегментов.
`focus` и `zsic` вкомпилируются (`-DUPPE_FOCUS_CM`, `-DUPPE_ZSIC_CM`) и передаются всем сегментам
цепочки. Так же передаются `build_flags` — дополнительные опции CMake (только
`-DUPPE_{ENERGY_MJ,PRELENS_CM,A0_CM,RMAX,NR_OPT}=<число>`) — и `run_flags` — опции программы
(только `--snap-dz-cm <см>` и `--linear`). Из командной строки:

```sh
gh workflow run simulate.yml -f z_max=30 -f focus=20 -f zsic=18 -f tag=z30-old
gh workflow run simulate.yml -f z_max=none -f focus=100 -f zsic=90 -f tag=f100-z90
gh workflow run simulate.yml -f z_max=175 -f focus=100 -f zsic=1 -f tag=f100-z1-E5-nopre -f max_segments=25 \
  -f build_flags="-DUPPE_ENERGY_MJ=5 -DUPPE_PRELENS_CM=0 -DUPPE_A0_CM=0.01 -DUPPE_RMAX=40 -DUPPE_NR_OPT=2000" \
  -f run_flags="--snap-dz-cm 0.5"
```

Пока сегмент считает, `ci/stream_results.sh` раз в 10 минут выкладывает новые результаты в release
`sim-<tag>` (pre-release):

- `grids.tar.gz` — `SpSIC.dat`, `Incident.dat`, `parameters.dat` и файлы сеток (один раз);
- `segNN_Zaaaa-Zbbbb.tar.gz` — `res/{IS,Fl,Or,Ne,IO}` законченных снимков;
- `latest_segNN.tar.gz` — `res/Imax.dat`, `Nemax.dat`, `Energy.dat` (с начала расчёта), `log_segNN.txt`;
- `DONE.txt` — появляется, когда достигнут `z_max`.

`res/kw_THz` в release не попадает: снимки каждого сегмента лежат в artifact `kw-<tag>-segNN`
(`kw.tar.gz`, хранится 90 дней) на странице запуска этого сегмента.

Локально результаты забирает [`tools/fetch_results.ps1`](tools/fetch_results.ps1): раз в 5 минут
скачивает новые архивы из release и распаковывает их в `UPPE_<tag>` рядом с папкой репозитория
(обычная структура `res/...`). Скачанное запоминается в `.downloaded.json`, так что скрипт можно
останавливать и запускать снова; он завершается сам, когда появляется `DONE.txt`.

```powershell
powershell -ExecutionPolicy Bypass -File tools\fetch_results.ps1 -Tag z30-old
```

Если сегмент упал (код выхода не 0 и не 75), цепочка останавливается. Продолжить можно вручную с
последнего чекпоинта: `segment` = номер упавшего сегмента, `resume_run_id` = run id предыдущего
успешного сегмента, `code_sha` — из его лога (шаг **Record commit**), `focus`, `zsic`, `z_max`, `build_flags` и `run_flags` — те же. Новую цепочку с тем же `tag`
можно начать только после удаления release и тега `sim-<tag>`.

Ограничения бесплатной машины GitHub для публичного репозитория: 4 ядра, 16 ГБ памяти,
не больше 6 часов на задачу (свободного диска на момент проверки было около 85 ГБ).

Первый запуск до 22 см за 5.5 часа прошёл от 18 до 20.79 см (1722 шага, около 11 с на шаг).
Шаг `dz` обратно пропорционален `Imax`, поэтому около фокуса (`Imax ≈ 550`) он около 0.0007 см.
Точнее оценить можно по `log_segNN.txt`: там есть `step time` и значения `z` в строках `Imax =`.

Каждый снимок (каждые 0.25 см, на участке 19–20.2 см каждые 0.1 см) занимает около 1.35 ГБ,
почти всё из них (1.34 ГБ) приходится на `res/kw_THz/Z*.dat`; остальные файлы снимка — около 1.8 МБ.
В `kw.tar.gz` снимок сжимается примерно до 0.5 ГБ; упаковка идёт около 95 МБ/с исходных данных,
выгрузка artifact — около 150 МБ/с.

Шаг `dz = 0.02·focus/Imax` растёт с фокусом. Если он сравним с интервалом снимков 0.25 см
(например, `focus = 100`, `zsic = 18`: `Imax` порядка 1–10, шаг 0.1–3 см), снимок пишется почти
на каждом шаге, и сегмент заканчивается по месту на диске (порядка 50 снимков), а не по времени.
Участок частых снимков 19–20.2 см задан в коде числами и от `focus`/`zsic` не зависит.

## Тесты

`tests/reference.hpp` — буквальные переводы фортрановских подпрограмм: полные комплексные
спектры в фортрановской индексации, наивное ДПФ с перестановкой половин, ганкелево
преобразование через `dot_product`, `JefThread_THz` построчно, `LinThread`/`KdivKZ`
с комплексным `exp` и `**20`, `FirstStep` по одной частоте. Тесты сравнивают с ними
оптимизированные ядра на малых сетках:

| Тест | Что проверяет |
|---|---|
| `bessel` | `J0`, `J1`, корни `J0` против табличных значений и против фортрановского поиска сканированием; `J0(корень)≈0` до n = 16000 |
| `fft` | соглашение о центрировании времени, нормировку, вложение ТГц-спектра в сетку `nt_all` |
| `hankel` | DGEMM-преобразование против `dot_product`, усечения по строкам/частотам, `E + 0.5k`, самообратимость |
| `propagation` | таблицы `kz`, `k_plasma`, фильтры, `LinThread`, `KdivKZ` |
| `nonlinear` | `JefThread_THz` целиком (с ионизацией и с выходом за таблицу) |
| `first_step` | `FirstStep`, `SpSIC.dat`, `Incident.dat` |
| `simulation_smoke` | два шага всей программы на уменьшенной сетке, все выходные файлы |
| `checkpoint` | 14 шагов подряд против 6 шагов + чекпоинт + продолжение: все файлы и итоговые чекпоинты совпадают побайтно; повреждённый чекпоинт отвергается |

## Оптимизации (все точно эквивалентны фортрановскому алгоритму)

1. **Эрмитово хранение и r2c/c2r FFT.** Все спектры эрмитовы (`HnkThread`, `LinThread`, `KdivKZ`
   задают `X(nt-i)=conj(X(i))`, бин Найквиста всегда 0), поэтому хранится только
   неотрицательная половина частот. Память и стоимость FFT уменьшаются вдвое.
   Фортрановская перестановка половин массива перед и после ДПФ эквивалентна умножению спектра на `(-1)^q`.
2. **Ганкелево преобразование как блочный DGEMM.** Вместо `dot_product`, перечитывающего
   200 МБ матрицы для каждой частоты, — один вызов `cblas_dgemm` на блок частот.
3. **Усечение ТГц-преобразований.** `JefThread` читает и пишет только первые `nR_opt-1`
   радиальных точек, поэтому преобразование kr→r считает только их (все 4999 — только на шагах
   вывода, где нужен `IntSpT`), а r→kr суммирует только по ним. Моды, на которых фильтр
   `exp(-(kr/krmax)^20)` в точности равен 0, пропускаются. Вместе это ускоряет ТГц-часть примерно в 7 раз.
4. **Предвычисленные множители.** `kz` чисто мнимое, `k_plasma` вещественное — хранятся как
   вещественные массивы; не хранится 2-гигабайтный `kz` для сетки FirstStep.
5. **FirstStep.** Обрабатываются только частоты выше порога `1e-30*ISm`, все четыре ганкелевых
   этапа сделаны пакетно через DGEMM.
6. **Корни J0.** Начальное приближение Мак-Магона + метод Ньютона с той же точностью вместо
   сканирования с шагом `Rmax/16000`; каждый корень проверяется по смене знака и расстоянию до соседнего.
7. **Вывод.** Быстрое форматирование (`std::to_chars`) и параллельная подготовка строк больших файлов.

## Точное воспроизведение численных особенностей

- `pi = 3.1415926536` (усечённое значение, как в Фортране).
- Литералы одинарной точности воспроизводятся как `(double)(float)`: `1.6e-19` в `ROhm`,
  `4./0.4` и `31000/5.15/5.15` в `DC_Field`, `0.02` в `dz`, `0.1` и `20.2` в `z_flag`, `err=1e-12`.
- Сохранены особенности алгоритма: `P(0)` без членов с постоянным полем; оптические частоты
  ниже `int(wmax_THz/dw)` (127 бинов) не распространяются линейно; асимметричное зануление
  ТГц-окна в `kbuf`; `dJ_dt(nt_all-1) = dJ_dt(nt_all-2)`; `Ne_max` выводится после первой стадии RK.
- `write_params` вызывается до `PrepareKZ_opt`, поэтому в `parameters.dat` записываются
  `ng = 0` и `Ldisp = inf` — так же, как в Фортране.

## Отличия в выводе

- Числа записываются кратчайшим представлением, однозначно восстанавливающим значение
  (а не фортрановским list-directed форматом). Столбцы и их порядок те же.
- Мнимая часть поля `Et(t)` в `res/Or`, которая в Фортране содержит только ошибку округления
  (~1e-17), записывается как точный 0: в порте поле во временной области вещественное.
- В `res/kw_THz` для `kr > k` угол `asin(...)` не определён и записывается как `nan`
  (Фортран печатает `NaN`).

## Ошибки фортрановского кода и как они исправлены

- **Выход за границу таблицы ионизации.** `P_N2(floor(I0*E_abs2*1d-11))` читает за пределами
  массива при индексе ≥ 9999 (интенсивность ≥ 1e15 Вт/см²). Индекс ограничивается 9998,
  выводится однократное предупреждение и итоговое число таких обращений.
- **Гонка при записи `Incident.dat`** в `FirstStep`: поток 0 читал `Ebuf(it,:)`, который другие
  потоки могли ещё не посчитать. Файл пишется после завершения вычислений.
- **Бесконечный основной цикл**; код после цикла недостижим и освобождает невыделенные массивы.
  Добавлен `--z-max`, память освобождается корректно.
- **Отсутствующие папки `res/*`** приводили к ошибке. Они создаются автоматически.
- **Нормировка энергии.** `I0 = W0/(π^{3/2} a00² t0)` верна для гауссова пучка, а интеграл сверхгауссовой
  интенсивности `exp(-2(r/a00)^16)` по плоскости равен `π a00² S`, `S = Γ(9/8)/2^{1/8} ≈ 0.8636`. Фортран
  поэтому вкладывал в импульс 0.432 мДж вместо 0.5. Теперь `I0` делится на `S`, и энергия источника равна `W0`.
- **`P/Pcr` и `zself` в `parameters.dat`** считались по `a0` вместо `a00` (для `focus = 100`, `zsic = 90`
  выводилось 0.0063 вместо 0.54). Теперь `P = W0/(√π t0)`, `Pcr = 3.77 λ²/(8π n2)`, а `zself` (Марбургер,
  по `k0 a00²`) выводится только при `P > Pcr`. В уравнения распространения эти величины не входят.
