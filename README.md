# UPPE_THZ_DC на C++

Порт фортрановской программы `UPPE_THZ_DC` (`PARALLEL.f90` + `FME_r.f90`): распространение
оптического импульса и генерация ТГц-излучения в воздухе во внешнем постоянном поле
(UPPE для оптики и ТГц, схема RK2 с промежуточной точкой, ионизация по таблицам N2/O2,
керровская, плазменная и омическая нелинейности).

По умолчанию программа делает ровно то же, что фортрановский код: те же сетки, константы,
порядок операций, расписание вывода и те же файлы в `res/`. Добавлен только останов по `--z-max`.

## Зависимости

- CMake ≥ 3.21, компилятор C++17 с OpenMP.
- Один из двух бэкендов:
  - **MKL** (Intel oneAPI, Windows или Linux): FFT через FFTW3-обёртки MKL, BLAS через MKL;
  - **FFTW3 + OpenBLAS** (GCC/Clang): libfftw3 (double) и OpenBLAS ≥ 0.3.10.

BLAS и FFT вызываются из параллельных OpenMP-циклов, поэтому библиотеки работают
в однопоточном режиме (MKL линкуется как `sequential`, для OpenBLAS вызывается
`openblas_set_num_threads(1)`). Число потоков задаётся только OpenMP.

## Сборка

### Windows, Intel oneAPI (icx + MKL) — рекомендуется

```bat
call "C:\Program Files (x86)\Intel\oneAPI\setvars.bat" intel64
cmake --preset mkl-windows-icx
cmake --build --preset mkl-windows-icx
ctest --preset mkl-windows-icx
```

### Windows, Visual Studio 2022 + MKL

```bat
call "C:\Program Files (x86)\Intel\oneAPI\setvars.bat" intel64
cmake --preset mkl-windows-msvc
cmake --build --preset mkl-windows-msvc
ctest --preset mkl-windows-msvc
```

`setvars.bat` нужен и при запуске: он кладёт DLL MKL в `PATH`.

### Linux, MKL

```sh
source /opt/intel/oneapi/setvars.sh
cmake --preset mkl-linux
cmake --build --preset mkl-linux -j
ctest --preset mkl-linux
```

### Linux, GCC/Clang + FFTW3 + OpenBLAS

```sh
sudo apt install libfftw3-dev libopenblas-dev   # или аналог
cmake --preset fftw-openblas
cmake --build --preset fftw-openblas -j
ctest --preset fftw-openblas
```

Опции CMake:

| Опция | По умолчанию | Смысл |
|---|---|---|
| `UPPE_BACKEND` | `MKL` | `MKL` или `FFTW_OPENBLAS` |
| `UPPE_NATIVE` | `ON` | `-march=native` / `-xHost` / `/arch:AVX2` |
| `UPPE_BUILD_TESTS` | `ON` | собрать тесты |

`-ffast-math`, `/fp:fast` и режим icx по умолчанию (`-fp-model=fast`) отключены намеренно:
порт воспроизводит фортрановский порядок операций, а fast-math его меняет.

## Запуск

```sh
uppe_thz_dc [--z-max <см>] [--threads <n>] [--data-dir <папка>] [--out-dir <папка>]
```

- `--z-max` — остановиться, когда `z*Ldifr` достигнет заданного значения (в см).
  Без флага цикл бесконечен, как в Фортране; все файлы сбрасываются на диск каждый шаг,
  так что прерывание процесса вручную ничего не теряет.
- `--threads` — число потоков OpenMP (по умолчанию `OMP_NUM_THREADS` или все ядра).
- `--data-dir` — папка с `N2.dat` и `O2.dat` (по умолчанию текущая; копии лежат в `data/`).
- `--out-dir` — куда писать `res/`, `SpSIC.dat`, `Incident.dat` (по умолчанию текущая папка).
  Подпапки `res/IS`, `res/Fl`, `res/kw_THz`, `res/Or`, `res/Ne`, `res/IO` создаются сами.

Пример:

```sh
export OMP_PROC_BIND=close OMP_PLACES=cores
./build/fftw-openblas/uppe_thz_dc --data-dir data --out-dir run1 --z-max 30
```

Память при производственных размерах (`nt_all=524288`, `nR=16000/1000/5000`):
около 2.2 ГБ на этапе FirstStep и около 3.5–4.5 ГБ в основном цикле (из них ~16 МБ на поток);
фортрановская версия требует ~8 и ~7 ГБ.

## Запуск в GitHub Actions

Workflow [`.github/workflows/simulate.yml`](.github/workflows/simulate.yml) собирает программу
на `ubuntu-latest` (бэкенд FFTW3 + OpenBLAS), прогоняет тесты и считает до заданного `--z-max`.

1. Actions → **Simulate** → **Run workflow**.
2. Указать `z_max` (см), при необходимости `time_limit_minutes` (по умолчанию 330) и `run_tests`.
3. После завершения скачать `results.tar.gz` на странице запуска в разделе **Artifacts**
   (хранится 90 дней). В архиве `res/`, `SpSIC.dat`, `Incident.dat`, прочие файлы сеток и `log.txt`.

Ограничения бесплатной машины GitHub для публичного репозитория: 4 ядра, 16 ГБ памяти,
около 14 ГБ свободного диска, не больше 6 часов на задачу. Если `z_max` не достигнут за
`time_limit_minutes`, расчёт прерывается (в запуске появляется предупреждение), а файлы,
записанные к последнему шагу, всё равно попадают в артефакт. Продолжения с места остановки нет.

Чтобы понять, какое `z` успевает посчитаться, посмотрите в `log.txt` на `step time` и на шаг по `z`
(разность соседних значений в строках `Imax =`): за `time_limit_minutes` пройдено примерно
`60 * time_limit_minutes / step time` шагов. Шаг `dz` обратно пропорционален `Imax`,
поэтому около фокуса он становится мельче.

## Тесты

`tests/reference.hpp` — буквальные переводы фортрановских подпрограмм: полные комплексные
спектры в фортрановской индексации, наивное ДПФ с перестановкой половин, ганкелево
преобразование через `dot_product`, `JefThread_THz` построчно, `LinThread`/`KdivKZ`
с комплексным `exp` и `**20`, `FirstStep` по одной частоте. Тесты сравнивают с ними
оптимизированные ядра на малых сетках:

| Тест | Что проверяет |
|---|---|
| `bessel` | `J0`, `J1`, корни `J0` против табличных значений и против фортрановского поиска сканированием; `J0(корень)≈0` до n = 16000 |
| `fft` | соглашение о центрировании времени, нормировку, вложение ТГц-спектра в сетку `nt_all` |
| `hankel` | DGEMM-преобразование против `dot_product`, усечения по строкам/частотам, `E + 0.5k`, самообратимость |
| `propagation` | таблицы `kz`, `k_plasma`, фильтры, `LinThread`, `KdivKZ` |
| `nonlinear` | `JefThread_THz` целиком (с ионизацией и с выходом за таблицу) |
| `first_step` | `FirstStep`, `SpSIC.dat`, `Incident.dat` |
| `simulation_smoke` | два шага всей программы на уменьшенной сетке, все выходные файлы |

## Оптимизации (все точно эквивалентны фортрановскому алгоритму)

1. **Эрмитово хранение и r2c/c2r FFT.** Все спектры эрмитовы (`HnkThread`, `LinThread`, `KdivKZ`
   задают `X(nt-i)=conj(X(i))`, бин Найквиста всегда 0), поэтому хранится только
   неотрицательная половина частот. Память и стоимость FFT уменьшаются вдвое.
   Фортрановская перестановка половин массива перед и после ДПФ эквивалентна умножению спектра на `(-1)^q`.
2. **Ганкелево преобразование как блочный DGEMM.** Вместо `dot_product`, перечитывающего
   200 МБ матрицы для каждой частоты, — один вызов `cblas_dgemm` на блок частот.
3. **Усечение ТГц-преобразований.** `JefThread` читает и пишет только первые `nR_opt-1`
   радиальных точек, поэтому преобразование kr→r считает только их (все 4999 — только на шагах
   вывода, где нужен `IntSpT`), а r→kr суммирует только по ним. Моды, на которых фильтр
   `exp(-(kr/krmax)^20)` в точности равен 0, пропускаются. Вместе это ускоряет ТГц-часть примерно в 7 раз.
4. **Предвычисленные множители.** `kz` чисто мнимое, `k_plasma` вещественное — хранятся как
   вещественные массивы; не хранится 2-гигабайтный `kz` для сетки FirstStep.
5. **FirstStep.** Обрабатываются только частоты выше порога `1e-30*ISm`, все четыре ганкелевых
   этапа сделаны пакетно через DGEMM.
6. **Корни J0.** Начальное приближение Мак-Магона + метод Ньютона с той же точностью вместо
   сканирования с шагом `Rmax/16000`; каждый корень проверяется по смене знака и расстоянию до соседнего.
7. **Вывод.** Быстрое форматирование (`std::to_chars`) и параллельная подготовка строк больших файлов.

## Точное воспроизведение численных особенностей

- `pi = 3.1415926536` (усечённое значение, как в Фортране).
- Литералы одинарной точности воспроизводятся как `(double)(float)`: `1.6e-19` в `ROhm`,
  `4./0.4` и `31000/5.15/5.15` в `DC_Field`, `0.02` в `dz`, `0.1` и `20.2` в `z_flag`, `err=1e-12`.
- Сохранены особенности алгоритма: `P(0)` без членов с постоянным полем; оптические частоты
  ниже `int(wmax_THz/dw)` (127 бинов) не распространяются линейно; асимметричное зануление
  ТГц-окна в `kbuf`; `dJ_dt(nt_all-1) = dJ_dt(nt_all-2)`; `Ne_max` выводится после первой стадии RK.
- `write_params` вызывается до `PrepareKZ_opt`, поэтому в `parameters.dat` записываются
  `ng = 0` и `Ldisp = inf` — так же, как в Фортране.

## Отличия в выводе

- Числа записываются кратчайшим представлением, однозначно восстанавливающим значение
  (а не фортрановским list-directed форматом). Столбцы и их порядок те же.
- Мнимая часть поля `Et(t)` в `res/Or`, которая в Фортране содержит только ошибку округления
  (~1e-17), записывается как точный 0: в порте поле во временной области вещественное.
- В `res/kw_THz` для `kr > k` угол `asin(...)` не определён и записывается как `nan`
  (Фортран печатает `NaN`).

## Ошибки фортрановского кода и как они исправлены

- **Выход за границу таблицы ионизации.** `P_N2(floor(I0*E_abs2*1d-11))` читает за пределами
  массива при индексе ≥ 9999 (интенсивность ≥ 1e15 Вт/см²). Индекс ограничивается 9998,
  выводится однократное предупреждение и итоговое число таких обращений.
- **Гонка при записи `Incident.dat`** в `FirstStep`: поток 0 читал `Ebuf(it,:)`, который другие
  потоки могли ещё не посчитать. Файл пишется после завершения вычислений.
- **Бесконечный основной цикл**; код после цикла недостижим и освобождает невыделенные массивы.
  Добавлен `--z-max`, память освобождается корректно.
- **Отсутствующие папки `res/*`** приводили к ошибке. Они создаются автоматически.

## Статус проверки

запуском на целевой машине: `cmake --preset ...`, `cmake --build --preset ...`, `ctest --preset ...`.
